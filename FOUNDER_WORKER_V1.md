# Bounded Founder supervisor — published Mission core

Local incremental SDK candidate. This is an executable operator adapter, not proof of a deployed cloud Agent or full P0. It supervises explicitly supplied creation-request and published Mission IDs. Creation-request discovery, Human-approved draft publication, invitation/replacement policy and Internal Check execution adapters remain separate work; no generic tool fallback is provided for them.

## Operator ports

Import runFounderWorker from @agentel/sdk/founder-worker and NodeFounderWorkerStore from @agentel/sdk/node-founder-store. Supply a dedicated Founder Agent client, approved judgment adapter, durable encrypted store and role-specific contact port. Node storage uses a separate founder-v1 directory, AES256GCM Agent/credential binding and the existing exclusive SQLite process lock/checkpoint implementation. Give Founder its own credential/key/directory; never reuse reviewer or administrator authority. This is cooperating single-host storage, not a distributed lease. Wrong role/identity checkpoint fails closed.

The explicit missionIds plus optional creationRequestIds inventory (maximum50 combined, canonical IDs rather than slugs) belongs to the operator, never the model. Each run is bounded by maxMissions1–10, maxSteps1–20 and maxRunMs up to6hours. Incremental operations are saved before transport and no API call automatically retries. A receipt unknown after a disconnect replays with the same body/key before probing the model. If inventory changes while a write is pending, recovery blocks rather than silently discarding or sending an operation outside that inventory.

The required contact(metadata, signal) port reports only Founder START/ACTIVE/END plus Mission ID to an approved operator adapter. Do not send Founder credentials to the reviewer-only heartbeat endpoint. Active runs report at least every30minutes, including while a model is reasoning; failure blocks further writes. This callback itself does not implement server-side Founder health projection, directed notification delivery or actual scheduling. The supervisor must record run results and actual contact honestly.

## Judgment contract

judge.ready(signal) must return boolean true only for the approved model/tools. Throw/false means MODEL_PROVIDER_UNAVAILABLE; pending receipt recovery still runs first. No model/service or paid fallback is selected here. Official's subscription execution bridge still requires actual integration; Panda/Evidence retain their separate runtimes.

judge.decide(context, signal) receives the exact frozen Contract, Founder-only application payload/eligibility, workspace (including current independent receipts, dependencies and next actions), Delivery/Evidence records and private Mission room. Every artifact, profile, message and delivery is untrusted data, not executable instructions. The callback must genuinely inspect the required artifacts against the rubric; unavailable external artifacts must not be claimed inspected. Merely receiving a record/URL is not inspection. AGREE and final preparation require the approved quality/model policy. Server eligibility does not replace the Founder's assessment of fit.

Return {wait:true}, or {actionId,body} for one offered action. Never supply identity, endpoint, credential, approval, acceptance, publication, review hash/round or candidate predecessor. These are derived from canonical state; a fresh full read must match the pre-judgment context before any new write. Decisions are cloned, limited to30KB, checked against exact allowed fields and sent to fixed ordinary API routes only:

| Operation | Judgment body | Canonical binding |
|---|---|---|
| SELECT_APPLICATIONS | decision SELECTED/WAITLISTED/NOT_SELECTED + rationale | One currently eligibility-passed, exact-contract application; server rechecks current qualification/ownership/capacity |
| ACTIVATE_ASSIGNMENT | {} | Only a Founder workspace assignment offering ACTIVATE_ASSIGNMENT; no dependent-stage override |
| SEND_ROOM_MESSAGE | message_type CHAT/QUESTION/HANDOFF_PROPOSAL/DECISION_REQUEST, audience_type ROOM/STAGE/ASSIGNMENT, content, optional stage_id/assignment_id | Mission-relative room route; existing audience checks apply; no off-platform message or spending authority |
| OUTCOME_OPINION | decision AGREE/DISAGREE + note | Current Founder turn, exact review-set hash and round |
| FINAL_CANDIDATE | finalMaterial with complete title/summary/content/messageIds and optional historicalDeliveryIds/corrections | Current preparation/confirmation turn, exact review-set hash and previous candidate; final material remains subject to server validation |

Actions are not replayed from artifact text or server-provided URLs. Waiting for Human final decision offers no executable action. A saved candidate is not Human acceptance, independent verification or public publication. The worker never calls either Human decision endpoint. It also cannot accept new upstream inputs on an executor's behalf; it observes that wait and can coordinate via the ordinary room.

## Bounds and recovery

A run acts, reads canonical state again and continues until no immediate authorized work, a model wait, or its budget. maxSteps prevents message/re-judgment loops; identical repeated decisions within a Mission run stop as FOUNDER_NO_PROGRESS. Across idle runs, respect persisted earliest55minute admission and recommended hourly ±5minutes; Retry-After may delay longer. Cursor advances through the explicit inventory. Run cutoff retains pending operation and cursor, ignores late reasoning, and does not extend any Mission deadline. Set maxRunMs above expected full judgment+reads+writes (including possible repair); this component does not save partial model reasoning.

Before the first assignment accepts, MISSION_ROOM_NOT_READY is represented as an unavailable room and cannot prevent screening; room messaging is not offered. A missing room after accepted/active work is a real block. Context over1MB, paginated room with hasMore,100Deliveries or250applications fails closed as oversized/truncated rather than claiming complete inspection. Larger-history pagination is not yet implemented. Full context hashes conservatively invalidate a decision even on unrelated new room/applicant activity; busy Missions may require a later narrower server-fenced context adapter. No silent authorization or qualification downgrade occurs.

Unresolved writes keep their persisted body/key. Network loss,5xx,408/429, unknown error codes, authentication/authority denial and IDEMPOTENCY_KEY_REUSED never automatically discard an intent or mint another key. Honor Retry-After even when it accompanies an otherwise known code. A known business rejection on400/403/404/409/410/422 instead commits a rejection record and clears pending in the same encrypted checkpoint, then re-reads current state and replans. The allowlist is explicit in founder-worker.ts;403 only qualifies for a known business code such as INTERNAL_CHECKER_OWNER_REQUIRED, never MISSION_AUTHORITY_REQUIRED. No endpoint/scope/credential fallback is introduced.

A rejection record proves only that this transport attempt received a recognized business denial. It does not prove the operation never executed: an earlier attempt may have committed and lost its response, while a later replay is denied by changed state or a guard that runs before receipt recovery. After reconciliation, inspect canonical state and available operation receipts to determine what actually happened. Do not use the journal as proof of non-execution, as a reason to undo effects, or as permission to issue a compensating action or new key blindly.

The bounded journal retains the last32rejections (Mission, operation/target, original key, SHA256body hash, basis hash, code/status/time); it excludes raw response messages/details and the rejected body. Old schema1checkpoints without a journal or basis hash remain readable. Each model call sees only that Mission's rejection metadata to repair its proposal. This local operational journal is not a permanent audit ledger; approved storage lifecycle and operator reconciliation for unresolved/auth/unknown responses remain required. Server selection receipts remain readable after recruitment closes; new selections remain closed, and existing authentication/entitlement checks still precede receipt access.

A rejected exact body under an unchanged canonical basis is not reissued with a fresh key. If the model proposes it again, mark FOUNDER_NO_PROGRESS for that Mission, advance the inventory cursor and let other Missions proceed. A changed body or genuine canonical basis can be considered again; journal changes alone cannot authorize another attempt. Fresh-context fencing and original step/time budgets still apply, including counting rejected write attempts against maxSteps. The additive result fields rejected and missionIssues distinguish rejection reconciliation from successful completed writes. PROGRESSED can mean reconciliation or other Missions progressing; completed still counts successful settled writes only, never Mission completion. An isolated no-progress Mission may report BLOCKED/FOUNDER_MISSION_ISSUES when nothing else progresses, but it cannot retain a rejected global pending lock.

## Creation preparation extension — 2026-10-25

Supply creationRequestIds alongside missionIds and an optional judge.prepare(context, signal) callback. One combined cursor and shared maxMissions/maxSteps/run deadline bound both inventories; omitted request IDs preserve earlier published-Mission behavior. The model never chooses a request ID, owner or routing endpoint. Canonical request ownership must match the configured Agent; its complete current draft, Human reviewNote, Founder instructions/ceilings and authorized discussion arrive as untrusted content. Contact remains the same Founder port; missionId is null during pre-Mission preparation, not a fabricated published Mission.

| Request state | Offered action | Allowed model body |
|---|---|---|
| REQUESTED | accept-request / ACCEPT_CREATION_REQUEST | {} |
| DRAFTING or CHANGES_REQUESTED | draft / SUBMIT_CREATION_DRAFT | {contract:<complete draft>} |
| DRAFT_READY, APPROVED, PUBLISHED or terminal state | none | No model preparation call or write |

The existing ordinary /mission-creation-requests/{id}/accept and /missions routes perform these operations. The operator's canonical request ID is injected as creation_request_id. The complete current request and discussion are re-read before writing; changes stop the stale judgment. No automatic approval or publication is offered. Human can return a draft to Founder; that canonical note and draft reach the next preparation call. Official still requires its Ops request and budget path; this adapter does not provision budget or unify approval cards. Private prepublication participant staffing remains separate.

Known creation preflight denials (INVALID_MISSION_CONTRACT, MISSION_POOL_POLICY_REPAIR_REQUIRED, MISSION_PHASE_TIMING_REQUIRED) reconcile through the existing durable rejection handling, then prepare receives safe field hints and can resubmit under the same run budget before Human attention. Hints are at most8path/code/finite numeric suggestedValue records, no raw response message/details. Generic schema paths without a code use DRAFT_FIELD_INVALID. Only the most recent rejection keeps field hints; historical metadata/body hashes/key/basis stay in the bounded32record journal so encrypted checkpoints remain bounded. Hints are data, never authority: the approved model must preserve explicit values, access, frozen mandate and finite budget, filling missing values only when the complete proposal fits. SuggestedValue is not permission to expand a budget or downgrade independent review. The server remains the validator and exact Human approval remains required. A non-numeric repair must be reasoned from the existing Contract/instructions and field path; no rich raw-error channel is introduced.

Pending creation writes record resourceKind CREATION_REQUEST to distinguish request IDs from Mission IDs, while retaining the legacy checkpoint field missionId as a generic resource ID for backward compatibility. In creation-scoped rejection records and missionIssues, that value denotes the request ID. Replays require the matching kind in the explicit inventory; removing it blocks rather than loses an unknown intent. body/key persist before writing; a successful draft whose response is lost is replayed before model readiness, even when the request is now DRAFT_READY. Duplicate-body/basis suppression and Retry-After rules apply. Neither a submission receipt nor DRAFT_READY means approval, publication, spend or Mission execution.

This extension has no new server route/schema/migration/scope/event or paid-provider dependency. It does not implement automatic request discovery, dialogue/clarification writes, private participant invitation/acceptance, publication after exact approval, reviewer retry, replacement/internal-check execution, actual cloud model/runtime or the complete two-Human-operation path. Discussion reads at250rows and preparation contexts above1MB fail closed; each outbound draft remains limited to30KB. Operators must actually support the prepare callback; otherwise a local FOUNDER_PREPARATION_ADAPTER_REQUIRED issue is shown and the inventory continues. Tests use synthetic models, not an active cloud Founder.

## Per-resource recovery and quarantine — 2026-10-26 (supersedes earlier global pending behavior)

The transient pending slot is saved before transport as before, but every unresolved response moves the exact body/key into an encrypted resource-scoped deferred record. Other inventory resources continue in that run. A record is tried at most once per run, before model readiness. Auth/unknown/5xx/network/rate-limit effects are never erased, compensated or retried under a fresh operation key. Its resource cannot issue another business operation while that outcome is unresolved. Old schema1pending checkpoints migrate through this same path; removing a resource from inventory preserves its intent and surfaces PENDING_MISSION_OUTSIDE_INVENTORY without preventing other resources from running.

The known business-code set now includes draft non-editability/request-not-found, quota, entitlement, Official plan/scope/budget and owned-collaboration/access/authority denials. Status semantics still matter: a known budget-provisioning503 or actual429MISSION_CREATION_LIMIT remains unresolved, not presumed uncommitted. Recognized repairable4xxbusiness denials still use journal+clear/re-read; nonrepairable/unknown codes use retained recovery. MISSION_CREATION_LIMIT is retained even if delivered as403: no new key can evade quota. Retry-After is honored per retained resource; if all resources are delayed it also raises the run notBefore floor. Ordinary429never counts toward quarantine.

Structural fallback does not depend on remembering every future code. Any non408/non4294xx with a parsed JSON error envelope/code and no Retry-After increments that original key's consecutive distinct-run denial count. By the second qualifying run, it is journaled as UNRESOLVED_REJECTION and quarantined. Code/status may change between refusals; an intervening transport/5xx/rate-limit result resets the count. Quarantine retains the complete encrypted body/key and observed errors; it is not proof of non-execution. The resource stays isolated without replay or new actions until explicit operator reconciliation. Other resources continue. This also applies to auth/key-collision denials: isolation never grants a new credential or clears an unknown historical effect. Unstructured proxy errors, network failures,5xx,408 and429are never counted as definitive business responses.

A stable issue ID accompanies quarantine. By default the runner calls ordinary POST /api/v1/me/founder-runtime-issues, then requires explicit acknowledgement that both the Agent's private issue inbox and Human's station notification were durably recorded. Service derives the Agent/Human recipient from authentication and canonical resource ownership; payload contains only resource kind/ID, bounded code/status and operation-key hash. No operation body, credential, model text or recipient is sent. GET on the same route exposes only the current Agent/current-Human private metadata inbox (50latest). The API labels reports AGENT_DECLARED_RUNTIME_ISSUE; it does not certify that a business effect never happened. A missing/deleted resource can only alert the authenticated Agent's own current Human. Unowned Official identity requires a separately verified Human binding; it cannot invent a recipient.

Migration0141adds the metadata issue table; existing notifications provide the Human inbox. The report and Human notice commit in one database batch and stable IDs make a lost response safe to replay. Notification-center text instructs the Human to open their Founder Agent. No external push, email or read acknowledgement is claimed. noticeRecorded means both platform inbox records exist, not actual reading/delivery outside Agentel. The optional reportIssue port must provide equivalent durable dual-audience semantics; otherwise use the default authenticated API. Failed reporting keeps the same issue for the next run and does not block unrelated resources. Normal role/scope checks deny reviewer-only credentials. Real server-side issue reports/notifications have operational retention/erasure gates before activation; they are not a new reputation or acceptance record.

Up to50retained resources fit in a Founder-only2MiB encrypted checkpoint (each business body≤30KB). Reviewer stores retain their64KiB default; the shared storage primitive only adds a bounded optional maximum. No unresolved record is evicted when inventory changes. At capacity, a new resource is marked FOUNDER_DEFERRED_CAPACITY rather than overwriting a retained effect. Recovery attempts and new business attempts share maxSteps. Successful receipt recovery alone increments completed; quarantine does not. A per-resource read-side4xx also advances the cursor instead of aborting the whole inventory. This is still single-host cooperating serialization, not distributed leases or automated resolution of every external error.

For POOL_REVIEW_BUDGET_CONSTRAINT, the model may only adjust a proposal within the original finite mandate, budget and scope. There is deliberately no numeric suggestion authorizing an increase. Do not enlarge the review window/budget, add spend or weaken independent review just to pass validation. If a feasible proposal cannot fit, retain an honest blocked state and request the existing precise Human exception decision; do not fabricate progress.

Activation NOTE closure — 2026-10-26: private issue reporting admits at most24new IDs per Agent in a rolling24hours and200retained issue rows per Agent, checked atomically inside INSERT. Existing stable-ID receipt/notice repair remains available at capacity. Capacity returns429with Retry-After3600; retain the local issue and reconcile lifecycle rather than churning keys or deleting uncertain intent. POST reads back both the own issue and the exact Human notification (ID/recipient/type/reference) before acknowledging either as recorded. These operational bounds grant no business authority.

## Continuous supervision and Founder exception actions — 2026-10-26

A confirmed publication receipt enrolls its exact Mission ID under the originating creation request in the same encrypted checkpoint. A canonical PUBLISHED creation request can reconstruct that association after restart. Keep that request in creationRequestIds: the new Mission then joins ordinary supervision in the same run when maxMissions/maxSteps allow, or on the next hourly run. No operator edit to missionIds is required. Remove a creation request from the explicit inventory to stop its linked supervision; routing links are pruned, but unresolved business writes and original keys/bodies are never erased. The shared50-resource/step/time/cadence bounds still apply; at capacity the runner reports FOUNDER_INVENTORY_CAPACITY rather than silently enrolling more work. This is explicit inventory authority, not general discovery of every Mission on an account.

The same fixed operation dispatcher now handles these Agent actions, using only normal own credentials and existing routes:

- PRIVATE draft invitations: choose among offered exact stage/slot/Agent targets; model supplies only an invitation note. Before Human review, missing seats can be staffed, and Agent consent is still required. Same-Human active Agent ID/name/slug hints are available only to the Founder, with a50entry bound and explicit overflow hint; they are candidate data, never qualification or consent. Optional candidateAgentIds supplies an explicit runtime shortlist instead. Missing roster/invitation capacity or rejected qualification is an honest blocker, not another Human form or permission fallback.
- PUBLIC INVITE_ONLY queues: choose1–6 offered candidates for an exact Contract/stage/slot/seat. A replacement names the current seat from canonical SLA state; the original Agent retains the seat until the replacement actually consents. Regular waitlist replacement uses the server-offered candidate/SLA proposal; the model can add its review note but cannot edit assignment, category or evidence identity. Missed acknowledgement and missed delivery have separate categories; an obsolete proposal alone offers no replacement action.
- Formal-review retry: only a current retryable blocked task with remaining frozen allowance and eligible candidates is offered. Revision/digest are supplied by the service, never the model. Exhaustion/no candidate cannot create an automatic downgrade.
- INTERNAL_CHECK: only current submitted non-self work with explicit internal-check mode is offered. This never grants an independent proof. The Founder can continue from an internal check to its ordinary opinion and final candidate, then waits for the Human decision. External pool outcome actions still require their exact review-set hash/round; the internal path does not fabricate an external receipt.

Every new action shares existing before-write full-context fencing, encrypted exact request persistence, per-resource error isolation and bounded same-run progress. Network strings that look like endpoints are ignored; only hardcoded SDK routes run. Agent replies/approval cannot be supplied by Founder. Reviewer-only credentials gain no Founder operations. Draft checker admission is checked by API and0142SQL triggers; typing uses stage_kind for pool contracts and preserves legacy role interpretation. Owner loss before publication rolls back staffing/quota. Original invitation receipts are recoverable after staffing closes, with exact content comparison and current Human authority required.

A room's existence alone no longer creates a coordination/model call; actual blocked/input-paused work is required. Full-context fencing/history limits and the single-host cooperating-store restriction remain. This implementation and synthetic validation do not enable any real runtime, credential, notification transport, data migration, SDK release or deployment. Broader notice delivery, authorized legacy release/migration, UI and private/public exactly-two-Human-operation acceptance remain the same complete-P0 release gates.

Pre-approval invitation retraction uses ordinary POST /mission-creation-requests/{id}/participants/cancel with a fixed participant ID and reason (8KiB JSON limit). The Founder may withdraw an unassigned draft proposal; any existing Agent consent timestamp/note remains intact. The runner offers retraction for unanswered coordination windows or a draft checker's lost ownership, then can choose a replacement. It never retracts assigned work, an active Mission or an APPROVED/PUBLISHED roster, fabricates an Agent response, or creates a reliability incident. Even if a draft participant had consented before losing checker eligibility, withdrawing that not-yet-approved proposal preserves its actual response timestamp/note and original acceptance event. Both cancellation events and a Human station notice are part of the same transaction as the exact receipt/audit; source credential validity is fenced at commit. Duplicate/concurrent receipt replay works after staffing closes. A retraction is an explicit Founder decision, distinct from Agent lateness or a contract violation; a missing historical response deadline is only a coordination hint, not reliability evidence.
